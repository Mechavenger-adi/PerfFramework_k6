## Completed Tasks

- **Interactive Command Panel (Proposal 4):** New menu-driven entry point at `core_engine/src/cli/interactive.ts`. Launched by bare `k6-framework` / `npm run cli` on a TTY (non-TTY falls through to commander's help so CI is unaffected) or explicitly via `k6-framework menu`. Three groups (Author / Run / Project) covering twelve actions: Generate from HAR, Convert native k6 → framework, BYOS scaffold, Import cURL (clipboard / file / paste), Import Postman (with top-level folder picker), Run a test plan, Debug replay, Validate plan, Init project, List/show templates, Inspect resolved config, List features. Thin orchestrator — every wizard collects inputs via `readline/promises` and delegates to the existing CLI handler (no logic duplication). Workspace detection on entry: if cwd has neither `config/` nor `testSuites/`, prompts to `init` first. Team picker auto-scaffolds `testSuites/<team>/{tests,data,recordings}/` when creating a new team. File pickers glob cwd + immediate subdirs for `.har`/`.postman_collection.json`/`.js` (skips `node_modules`/`.git`/`dist`/`results`) with manual-path fallback. Test-plan picker lists `config/test_plans/*.json`. cURL input modes: clipboard (default — pairs with browser "Copy as cURL"), file path (multi-curl supported), paste-here (read until blank line). `run` / `debug` re-spawn the CLI as a child process so the ANSI scroll-region live table doesn't fight the menu's readline display. Per-action errors are caught and surfaced; SIGINT trap exits cleanly. Bonus bug fix bundled: `--curl '<string>'` mode now runs the same `splitMultiCurlFile` splitter as `--file`/`--stdin`/`--clipboard`, so a leading `# Transaction name` line in inline input is honored. All existing direct CLI commands continue to work unchanged. See `ai_context/design-proposals.md` → Proposal 4 for the full design.
- **Request Import — Phase 2 (Postman):** `import postman <team> <script-name> --file <collection.json> [--folder <name>]` CLI command. In-house Postman Collection v2.1 parser (`core_engine/src/recording/PostmanAdapter.ts`), no new runtime dependency. Folder → `TransactionGroup`, request → `HAREntry`. Nested folders flatten via dot notation (`API.Auth.Login`). Top-level (no-folder) requests get their own single-entry group named after the request. URL: handles both string and `{raw, host[], path[], query, ...}` object forms. Headers: filters `disabled: true` entries; supports both array and raw-string forms. Body: raw (with language-aware mime), urlencoded (filters disabled fields), formdata (warning + JSON repr), file/none. Auth (request-level only, no cascade): bearer/basic/apikey → emitted as headers; oauth2/digest/etc. → warning. Pre-request/test scripts: emit warnings (NOT in-script TODO comments — would have required emitter changes, violating Phase 2 "no emitter changes" constraint). Postman `{{variable}}` references preserved literally for user to wire to env/CSV after generation. Insomnia format deferred to a future Phase 2.5. See `ai_context/design-proposals.md` → "Request Import" → "Phase 2" for the full scope.
- **Request Import — Phase 1 (cURL):** `import curl <team> <script-name>` CLI command. Produces a framework-shaped k6 script from a cURL command (inline `--curl '...'` string or `--file <path>` containing one or more blank-line-separated curls). Multi-curl files honor leading `# Transaction name` comments to name each transaction. Adapter: `core_engine/src/recording/CurlAdapter.ts` (in-house parser, no external dep; covers `-X`, `-H`, `-d`/`--data`/`--data-raw`/`--data-binary` with `@file` resolution, `-u user:pass`, multi-line `\` continuations; unsupported flags emit warnings and continue). Smoke-tested: single-curl POST with JSON body + basic auth → base64 Authorization header + hoisted env baseUrl; multi-curl file with 3 named transactions + empty body + Bearer token → `thinktime()` between transactions. Mid-implementation: fixed a tokenizer bug where empty quoted strings (`-d ''`) were dropped. See `ai_context/design-proposals.md` → "Request Import" for the full phased plan. - **Live Metrics Display Overhaul:**
  - `startLiveTransactionDisplay` now uses an ANSI **scroll region** to split the terminal: k6 owns rows `1..(tableTop - 1)` (banner + animated progress bar live there, can scroll naturally), and the live metrics table is frozen at the bottom in rows `tableTop..termRows`. Render flow per tick: `\x1b7` save cursor → clear table area → draw new table at `tableTop` → `\x1b8` restore cursor. k6's progress bar continues animating without ever touching the table area, and the table updates in place (no scrollback churn). Helper split: `buildLiveTableLines` returns the styled strings; `renderFixedTable` does the scroll-region/cursor dance; `renderScrollbackTable` is the fallback used when stdout isn't a TTY or the terminal is too short (`termRows < tableRows + 12`) to fit both regions.
  - On `stop()`, the scroll region is reset (`\x1b[r`) and the cursor is parked below the table so post-run output (transaction summary table, etc.) appears below cleanly.
  - Corrected pass/fail formula. Old logic used `count - min(checkPasses)` which silently reported `0` fails whenever the `checkPasses` map was empty (e.g. when all checks for a transaction were failing). New logic computes `failedIterations = min(max(checkFails), count)` and `pass = count - failedIterations`, with a `count` fallback when no check data exists at all.

## Current / In-Progress Tasks

- **Lifecycle Redesign V2 (per `design_proposal.md`):** Reliable, proactive, VU-driven `endPhase` (logout) across all executors. Full design captured in root `design_proposal.md` (proposal body starts at line 11). Root cause being fixed: k6 has no per-VU teardown hook, and the current (V1) detector triggers logout *reactively* at/after k6's VU removal (`lifecycle.ts` `getEndSignal` → `vuId > target`), so the logout iteration never arrives. V2 makes each VU compute a **proactive deadline** and self-exit a margin *before* k6 removes it.
  - **DONE — Graceful passthrough:** `gracefulRampDown` / `gracefulStop` now flow to k6. Added to `GlobalLoadProfile` (`TestPlanSchema.ts`), `K6ExecutorConfig` + `toK6ExecutorConfig` (`WorkloadModels.ts`), `K6ScenarioDefinition` (`ScenarioBuilder.ts`), and `global_load_profile.properties` (`config/schemas/test_plan.schema.json`). Unset → omitted → k6 keeps its 30s defaults (zero behavior change unless set). Usable in any `global_load_profile` or per-journey `loadProfile`.
  - **DONE — V2 lifecycle engine** in `lifecycle.ts`, gated behind env var `K6_PERF_LIFECYCLE_V2=true` (k6 inherits system env). V1 path untouched when the flag is off.
    - `terminalDeadlineMs(curve, vuId)` = `sup{ t : target(t) ≥ vuId − 0.5 }` — last permanent downward crossing. Correct for load/soak/stress/step-down/spike/multi-spike (look-ahead avoids premature logout of VUs k6 will reuse); survivors get total duration → logout under `gracefulStop`. The `−0.5` half-step is the margin that makes the VU self-exit just before k6's integer removal.
    - `computeEndPlan(phases)` → per-VU `EndPlan` by family: **ramping** (deadline; also covers constant-vus via its synthetic ramping envelope), **count** (`per-vu-iterations` / `shared-iterations`, deterministic last-iteration; zero-work shared VUs end before any action), **arrival** (`constant/ramping-arrival-rate` → action-only, init/end disabled + one-time runtime notice), **external** (best-effort, no auto-end).
    - `runJourneyLifecycleV2()` shell: init-once (or arrival notice) → boundary end-check → action → post-action end-check. Either check fires while the VU is still scheduled (deadline < k6 removal), so `endPhase` always runs, then the VU parks and k6 reclaims it harmlessly.
    - `isEnding()` exported (and from `index.ts`) for long action loops: `while (!isEnding()) { transaction(...); thinktime(); }`. `getTransactionGate()` consults the V2 plan when the flag is on.
  - **TODO — remaining for V2 to reach the full design:**
    - Make the flag discoverable: add a `runtime_settings` option (e.g. `lifecycle.v2`) that injects `K6_PERF_LIFECYCLE_V2` via `buildScenarioEnv`, instead of relying only on the OS env var.
    - §8 fully-native constant-vus: stop emitting the synthetic `→0` ramp in `ScenarioBuilder.computePhaseEnvelope` (`ScenarioBuilder.ts:337-349`); emit real `durationMs`+`vus` and compute `deadline = duration − margin` with an optional load-preserving vuId stagger. (V2 already improves constant-vus by reinterpreting the synthetic timeline, but this removes the executor-misrepresentation + end-of-test load shave.)
    - Strategy D (`externally-controlled`): add the heartbeat end-check (currently never auto-logs-out).
    - Arrival-rate UX: prompt author to put everything in `actionPhase` at generation/conversion time (`generate`, `convert`, `LifecyclePrompt`); expose k6 `setup()`/`teardown()` to journey scripts for true once-only logic.
    - Generated/converted/scaffold scripts: adopt the `while (!isEnding()) { ... }` action-loop pattern in `ScriptGenerator.ts`, `ScriptConverter.ts`, `init.ts`, `generate-byos.ts`.
    - Validation: run load / soak / spike / step / constant-vus / iteration / arrival-rate plans with the flag on; confirm one clean logout per VU and gradual ramp-down. Then flip the default and retire V1.

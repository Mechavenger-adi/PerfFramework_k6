## Current / In-Progress Tasks

- **Lifecycle Redesign — proactive per-VU endPhase (DONE 2026-06-10, now the ONLY lifecycle):** Reliable, proactive, VU-driven `endPhase` (logout) across all executors. The old reactive V1 detector (`getEndSignal` → `vuId > target`) and the `K6_PERF_LIFECYCLE_V2` toggle have been **deleted** — `runJourneyLifecycle` is now the single proactive engine, no flag.
  - **Graceful passthrough:** `gracefulRampDown` / `gracefulStop` flow to k6 (`GlobalLoadProfile` → `K6ExecutorConfig`/`toK6ExecutorConfig` → `K6ScenarioDefinition` → schema). Unset → k6 keeps its 30s defaults.
  - **Per-VU deadline ranked by ONBOARDING TIME (the key fix).** Root cause (confirmed from k6 source `lib/executor/ramping_vus.go` + `lib/execution.go`): k6 culls by internal **handle index** (highest first), which equals onboarding order — but `idInInstance` comes from a FIFO VU pool (`es.vus`, concurrent init + `ReturnVU` recycling) so it does NOT match cull order, and the handle index (`vuNum`) is never exposed to scripts. Fix: `computeEndPlan` computes `rank = round(interpolateTarget(curve, Date.now() − scenario.startTime))` on the VU's first iteration (curve value at onboarding = handle index + 1), and `terminalDeadlineMs(curve, rank)` = `sup{ t : target(t) ≥ rank }` = the VU's cull instant. No shared state, no k6 patch — works on stock k6.
  - **Three catch points + 5s safety margin.** `isEndDueBefore`/`isEndDueAfter` fire when `Date.now() + LIFECYCLE_END_SAFETY_MS (5s) ≥ deadline`, so the VU logs out ~5s before k6 culls it. The **transaction gate** (`getTransactionGate` published via `globalThis.__k6PerfTxnGate`; `transaction()` consults it, phase-scoped to action only) skips remaining action transactions mid-iteration so `endPhase` runs promptly. `isEnding()` exported for `while (!isEnding())` long-action loops.
  - **`computeEndPlan` families:** ramping (onboard-rank deadline; also constant-vus via synthetic envelope), count (`per-vu-iterations`/`shared-iterations`, last-iteration), arrival (`constant/ramping-arrival-rate` → action-only, init/end disabled + one-time notice), external (best-effort, no auto-end).
  - **Validated across executors (2026-06-10):** ramping-vus 6/6 (staggered, ids shuffle but timing is rank-based), per-vu-iterations 4/4, shared-iterations 4/4, constant-vus 4/4, constant-arrival-rate = action-only + notice (by design). V2 now runs with NO env flag (default and only path). `npm run debug` (per-vu-iterations) regression clean.
  - **`thinktime()` skips once ending (DONE 2026-06-10).** `thinktime()` now early-returns when `_currentPhase === 'action' && isEndDueBefore()`. Reason: the transaction gate skips remaining transactions once a VU is ending, but the `thinktime()` sleeps *between* them were still running — so a long final transaction + leftover think times could push the actionPhase return past `deadline + gracefulRampDown`, and k6 force-killed the VU before `endPhase`. Root-caused from a real 20-VU run: 19/20 logged out (ranking fine), the miss was the VU whose `add_to_cart` hung ~60s at the HTTP timeout (matrix: add_to_cart max=60208ms) — the long txn + remaining think times overran the 1m grace. Verified fixed: synthetic ramp with 4s grace + 3s think times now logs out 5/5 across runs.
  - **Residuals (honest, k6-structural):** (1) a **single transaction longer than `gracefulRampDown`** (e.g. an HTTP call that hangs to the 60s `http.timeoutSeconds`) can't be saved — k6 force-kills mid-transaction, before `endPhase`. Mitigate by lowering `http.timeoutSeconds` or raising `gracefulRampDown` above the worst-case single-transaction time. (2) simultaneous onboardings (`startVUs > 0` / very steep ramp) share a rank → that block front-loads its logout (safe, just not gradual). (3) multi-ramp recycling makes re-onboard ranks approximate. None are exact-fixable in-script (handle index hidden, no shared state, no teardown signal); `gracefulRampDown`/`gracefulStop` are the net. Not patching k6 (would need a forked binary; xk6 can't reach the executor's private runState).
